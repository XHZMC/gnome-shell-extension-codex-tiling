# Codex Tiling —— GNOME Shell 平铺窗口管理扩展

把窗口按二叉空间分割树（BSP tree）来管理：桌面上的窗口永远严丝合缝地铺满工作区，
没有空位、也没有重叠。支持 GNOME Shell 45–51（Wayland 与 X11 均可）。

## 空间布局逻辑

布局被限定成「屏幕 → 列 → 行」两层：

- **根节点**：整个工作区 —— 物理屏幕去掉上方面板与底部图标停靠区（Icon Area）占用的空间，
  也就是 `Meta.Workspace.get_work_area_for_monitor()`。面板/停靠区如果占位（Ubuntu Dock 默认占位），
  平铺区域会自动避开它。
- **第一层（列）**：屏幕被切成若干「分栏」（Columns），每列占满整列高度。
- **第二层（行）**：每个分栏内部竖着堆叠若干窗口，形成「行」（Rows）。
- **用户无法在一个「行」内再切出两列** —— 横向的插入一律发生在列一级：让相邻的那一整列
  腾出一半，被拖动的窗口成为一整列。引擎内部（`LayoutTree.splitNode()`）会强制维持这条
  规则：对分栏里的某个窗口做横向切分时，实际切的是它所在的那一整列。
- **两条不变量**：平铺区域永远被填满（没有空位）；**除了最大化的那个窗口**，
  任何两个窗口都不重叠（最大化窗口盖住别人是允许的）。
- **不参与平铺的窗口**：最大化的（布局被冻结，取消最大化后原样恢复）、最小化的
  （腾出的空间由邻居吸收）、以及**对话框等浮动窗口**（`windowFilter.js` 按窗口类型、
  `is_attached_dialog()`、`transient_for`、模态等判据排除；已在管的窗口会被持续复核，
  事后才「变成对话框」的——例如文件选择器——也会退出平铺）。对话框保持 mutter 给的位置，
  既不占平铺格子，也不受「不能重叠」约束 —— 它本来就该浮在父窗口上方。

## 安装

```bash
make zip                    # 生成 ../../outputs/codex-tiling@codex.local.zip
make install                # 安装到 ~/.local/share/gnome-shell/extensions/
gnome-extensions enable codex-tiling@codex.local
```

Wayland 会话需要注销再登录（X11 会话可以 `Alt+F2` → `r`）之后扩展才会被加载。
之后可以在「扩展」应用里开关它，齿轮按钮打开设置（等同 `gnome-extensions prefs codex-tiling@codex.local`）。

## 八条需求的实现对照

| # | 需求 | 实现 | 代码 |
| --- | --- | --- | --- |
| 1 | 空白桌面上第一个窗口铺满屏幕，且**不是**最大化 | 该桌面的布局树为空时，把窗口放进唯一的叶子并 `move_resize_frame()` 到整个工作区；如果它带着最大化状态，先取消最大化 | `TilingManager._placeNewWindow` |
| 2 | 打开新窗口 → 按通常方式参与平铺 | 新窗口**不再顶替**焦点窗口：切开当前最大的格子、上下平铺进去（如果桌面上原来有窗口最大化，焦点切给新窗口时它的最大化已被取消）。没有任何窗口会被最小化 | `TilingManager._placeNewWindow`、`_insertIntoLargest` |
| 3 | 恢复最小化的窗口 → 从左下开始平铺 | 还原的窗口切开**最左下**那个窗口的格子、和它上下均分（两级结构里就是占它的下半部分），再把这一栏的行高均分；不再回到最小化之前记住的位置 | `TilingManager._restoreWindow`、`_splitBottomLeft`、`_bottomLeftLeaf` |
| 4 | 拖到另一个窗口的四个边缘 → 与之平铺（新建分栏时所有分栏等宽）；拖到「分栏」（宽度相同、竖向排列的一组窗口）内部两个窗口中间，或两个分栏之间 → 在该处平铺；拖到另一个窗口上 → 交换位置（大小一并交换） | 松手时按指针位置判定：落在分界线（阈值内）→ 让分界线某一侧紧邻的那个单位（竖线旁是**一整列**，横线旁是**一个窗口**）腾出一半，被拖动的窗口贴着分界线插入；落在窗口格子的边缘带上 → 贴左右边时在旁边插出新分栏、贴上下边时在这一列里插出新一行；落在格子内部 → 交换两个窗口的位置与大小 | `dropTarget.planDrop`、`layoutTree.splitNode` / `columnRegion` |
| 5 | 拖动窗口边缘可联动调整其余窗口的大小 | 抓住边缘时把这条边的位置写回布局：**只有紧挨着这条边的两侧分栏改变尺寸**（各承担 ±Δ），其余窗口原样不动；松手后再精确对齐一次 | `layoutTree.setEdgeExact`、`TilingManager._onResizeProgress` |
| 6 | 通常的最大化行为；最大化窗口不参与平铺；取消最大化恢复此前的布局；从最大化的窗口切走时**只取消它自己的最大化** | 最大化期间布局被冻结、其它窗口留在各自格子里被盖住，取消最大化时按原布局放回来。**从最大化的窗口切到同一桌面上的另一个窗口时，只取消原来那个窗口的最大化**（它回到自己的格子），新聚焦的窗口保持普通平铺、不会被带着一起最大化；跨桌面切换不动。新窗口**自己带出来的**最大化（应用启动时主动最大化）会被取消，改为平铺 | `TilingManager._onMaximizeChanged`、`_dropMaximizeOnFocusChange` |
| 7 | 窗口移到别的工作区/显示器 | 先从旧布局里摘掉（其余窗口吸收空出的空间），再按窗口自身状态与目标桌面的情况安置：**最小化的窗口过去仍然最小化**（不参与平铺）；**最大化的窗口（含全屏）过去仍然最大化**，并接管那个桌面的「最大化位置」（原先那个最大化窗口让位回到自己格子）；普通窗口则按需求 1 / 参与平铺处理（空桌面铺满，非空桌面切开最大的格子放进去、上下平铺）。两种情况下目标桌面的其它窗口照常 | `TilingManager._relocate` |
| 8 | 窗口的布局不能有空位，窗口之间也不能重叠 | 布局始终是一棵树、叶子的矩形互不重叠且拼满工作区：窗口被最小化/关闭/移走时它的兄弟子树接管空位；被拖到无效位置的窗口会回到自己的格子；拖动中其它窗口实时让位；客户端有最小/最大尺寸限制时，改写分界线让其它窗口迁就它。最大化窗口盖住其余窗口（允许的重叠），对话框等浮动窗口同样不参与平铺 | `layoutTree._layoutNode`、`removeWindow`、`_applyLayout`、`_adoptActualSize` |

## 鼠标操作一览

| 动作 | 结果 |
| --- | --- |
| 拖到另一个窗口格子的左/右边缘 | 在它这一列旁边插出一个新分栏（相邻整列让出一半，列里的窗口一起变窄） |
| 拖到另一个窗口格子的上/下边缘 | 在它这一列里插出新的一行（与该窗口上下平分，宽度和整列一致） |
| 拖到分栏内部的横线（两个上下排列的窗口中间） | 在这个分栏里插进新的一行：被拖动的窗口与邻居平分，分栏里的窗口依然同宽 |
| 拖到两个分栏之间的竖线 | 插出一个新的分栏：相邻分栏整体让出一半宽度，它里面的窗口一起变窄、上下关系不变 |
| 拖到另一个窗口格子内部 | 两个窗口交换位置；拖回自己的格子则保持原样 |
| 拖动窗口的边缘 | 与该边重合的那条分界线跟着指针走，另一侧的窗口（以及同一子树里的窗口）实时缩放 |

落点预览都用**主题色**（GNOME Shell 的 `-st-accent-color`），分两种形态（见 `stylesheet.css`）：

- **插入型落点**（插到两个窗口之间、贴着某个窗口的边、贴着屏幕边缘）→ 直接高亮**那条间隙**：
  一条细长实心条（粗细 = `preview-border-width`，默认 6px）。表达的是「新窗口会出现在
  这条缝里」，而不是画一整个格子；
- **铺满空桌面 / 交换位置** → 目标格子：主题色淡填充 + 高亮实心边框（边框宽度同样是
  `preview-border-width`）。

两种预览共用同一个 `preview-border-width` —— 改一个值，格子的边框和间隙条会一起变粗变细
（最小 1px）。

## 几处需要说明的取舍

需求 2（已改）：新窗口**不再顶替**焦点窗口、也不会把任何窗口最小化，而是按通常方式参与平铺 ——
切开当前最大的格子、上下平铺进去（见下面「自动安置一律上下平铺」）。附属窗口（对话框、
浮动工具窗、跳过任务栏的窗口）不参与平铺；**「跟屏幕一样大」不再作为排除条件** —— 它
对刚退出全屏的窗口、以及「最大化过」的窗口同样成立，拿它驱逐会让窗口退出全屏后
再也回不到平铺里（见下面「全屏只是暂时状态」）。

需求 3：用户自己按最小化的窗口，还原时**从左下开始平铺**：切开「最左下窗口」（最靠下，
并列时最靠左）的格子，恢复的窗口占它的下半部分，然后把这一栏的行高均分（和「分栏内
窗口增减就均分」的规则一致）。锚点窗口本身不被挪动，只是让出一半空间。

布局是按**工作区对象**记账的，不是按它的索引 —— GNOME 的动态工作区在增删桌面后会把后面
所有桌面的索引整体前移，用索引记账会让布局串到别的桌面上（表现就是「系统自动增删桌面之后
平铺变得很奇怪」）。系统删掉桌面时顺手回收它的那份布局。

需求 7：把窗口移到别的工作区/显示器时，它从旧布局里摘出去（那里的其余窗口吸收腾出的空间），
到目标桌面按**它自己的状态**与那里的情况安置：最小化的窗口过去仍然是最小化的（不参与平铺）；
最大化的窗口（含全屏）过去仍然最大化，并接管那个桌面的「最大化位置」；普通窗口才参与平铺 ——
空桌面按需求 1 铺满，非空桌面切开当前最大的格子放进去（上下平铺），不抢别人的位置、也不把别人
最小化。两种情况下目标桌面的其它窗口照常。

**全屏只是暂时状态**：全屏期间窗口照旧留在布局里（只是不参与几何计算，也完全不参与
「最大化位置」的交接），退出全屏后回到它原来的格子。

`is_monitor_sized()` / `is_screen_sized()` **不参与「该不该平铺」的判断**：它在两处会误伤 ——
刚退出全屏的那一瞬间（几何还没缩回来）、以及退出全屏后回到「最大化」状态的窗口 —— 一旦
据此驱逐，窗口就再也不参与平铺了。窗口再大也只该被摆进它的格子里，真正要排除的是
对话框 / 附属窗口 / 全屏状态本身。

兜底复核每 2 秒跑一次；被摘出平铺的窗口（例如曾经的误判、或者对话框关系解除后）会被
记下来定期回看，重新符合条件（比如退出全屏、取消最大化）就自动接管回布局。

挪过来的最大化窗口只登记为「那个桌面的最大化窗口」、并不占格子（它盖住整个工作区，暂时不需要格子）。
一旦它的最大化被取消（切走焦点、取消最大化、被拖动），扩展会立刻把它按通常方式插进布局 ——
否则它会停在最大化时的几何上、既不在布局里也不再参与平铺。

**新加入平铺的窗口从「左下角」开始**：新窗口、恢复的窗口、挪过来的窗口，都是切开**最左下**
那个窗口的格子、占它的下半部分（`orientation: 'v'`），其它窗口的矩形一动不动 —— 所以平铺是
从左下角一路向上长出来的，不会突然出现在屏幕中间。不会自己切出新分栏：分栏只在用户明确把
窗口拖到某个窗口的左/右边时才产生。接管扩展启用前已有窗口时同样如此。

**几何只有一个写入者、且写的人越少越好**（这一版重写了这部分）：

- 套用布局时，已经在自己目标位置的窗口不会被再次请求几何；布局没变化时一个请求都不发；
- 窗口的几何请求一律用 `user_op = false`：这是「程序摆放」而不是「用户拖动」，
  合成器不会因此去挪动窗口（之前用 `true` 会让 mutter 为了满足约束去调整位置，
  看起来就是位置跳动）；
- shell 自己正在做动效时（概览 / 应用网格可见）不写窗口几何 —— 否则会和它的动画抢。
  但这些动作只是**延后**，不是丢掉：扩展连着概览的 `hidden` 信号，关掉之后把攒下的
  重新平铺 / 取消最大化补做一遍。从概览里开新窗口、把窗口拖到别的桌面、在概览里切换
  窗口全都发生在「概览可见」的瞬间 —— 直接丢掉就会出现「新窗口不参与平铺」「挪过来的
  窗口没加入布局」「切走焦点后原来那个最大化窗口还最大化着」；
- 延迟复核**只针对需要复核的那一个窗口**，没有「过一会儿把整张布局重套一遍」的兜底扫查
  （那是位置跳动的主要来源）；复核自带走完就停的判断：已经在自己的格子里就什么都不做，
  只有客户端确实没照做时才继续往下看（见下面「窗口有尺寸限制」）；
- 拖动 / 缩放期间，被拖动的窗口完全归合成器管：我们只调整**其它**窗口；拖动时不再去写
  它（写了就是互相拉扯），松手时按已经算好的边界精确落位。

**手动缩放只认指针**：抓住窗口边缘后，分界线的位置直接用**指针坐标 + 抓取瞬间的偏移**推算
（每 16ms 一次），不再等客户端确认新尺寸 —— 交互式缩放时窗口的新几何是异步生效的，跟着它走
会让边界永远慢一拍，表现出来就是抽搐、以及松手后不落在鼠标位置。松手时按这个边界精确对齐，
所以位置就是鼠标位置。

抓取瞬间的偏移以**布局里这个窗口的格子边缘**为基准，而不是窗口此刻的实际边缘：客户端可能
没照做（有尺寸限制）、或者几何还没生效，实际边缘离格子边缘很远 —— 拿它当基准，抓取的一瞬间
分界线就会跳到别处，连累到跟这条边无关的窗口。用格子边缘做基准，抓取那一刻分界线正好等于
布局现在的边界（一动不动），之后 1:1 跟着指针走。

**拖动时先从紧挨着这条边的两块改起，到了最小尺寸就由下一块接着让（级联）**：分界线移动
多少，先由两侧相邻的那两个「分栏」各自承担（一侧 +Δ、另一侧 -Δ），同一棵树里其余窗口
不动。如果被压缩的那一侧已经到 `minimum-window-size`，**剩下的位移继续交给「邻近的邻近」
那块**：例如「左中右」三栏里把左边拉大，中间那栏到最小后右边那栏接着变窄；「上中下」同理，
中间那行到最小后最下面那行接着让。不会像按比例联动那样连累整棵子树（以前拖动中间那栏的
右边框会把最左边那栏也带着变）。

例外是同一栏里上下堆叠的窗口：它们的宽度天然一致，所以拖动这一栏的左右边框时，栏内所有
窗口会一起变宽变窄（高度不受影响）。

为了把「只动这条链上的窗口」做成硬约束，另外做了两件事：

- **四角拖动 = 斜向调整**：mutter 在角落会同时给出两个方向（例如右下角），扩展就**同时**
  调整宽度和高度：横竖两条分界线各自 1:1 跟着指针、各自按最小尺寸停住，互不打架；指针
  停住时布局也不再漂。各方向仍然只动这条边两侧相邻的那一块。
- **每一步都校验**：级联的每一级之后核对「发生变化的窗口都在这一条链上」，整次级联结束时
  再核对一遍；万一有链外窗口被改动（例如遇到意想不到的布局形状），整次级联回滚并记一条
  日志 —— 宁可这一帧不动，也不连累无关窗口。

**分界线不会被「某个窗口曾经有多大」钉住**：拖动时唯一的约束是通用最小值
（`minimum-window-size`），扩展不去猜任何窗口的最小尺寸。客户端做不到更小/更大时，边界照样
跟着指针走，等**松手、几何稳定下来**之后才让布局迁就它（见下面「窗口有尺寸限制」）。曾经按
「观察到的最小尺寸」来钳制边界的做法会让相邻窗口突然被压到那个尺寸上、边界也不再跟着鼠标，
所以它被彻底移除了。

**拖动过程中不会被自己的自动调整干扰**：拖动 / 缩放期间，几何复核与尺寸限制自适应都不去碰
任何窗口（复核会让路，松手后重新安排）；被拖动的窗口完全归合成器管，我们只调整**其它**窗口。
边界被钳制住时（邻居已到通用最小值、或者已经贴到工作区边缘），被拖动的窗口松手后会**停在
真正的边界上** —— 既不会越过边界，也不会突然弹回。

**新分栏一律等宽**：插入新分栏之后，扩展会把根这一层（列与列之间）的分割比例按「各自还剩几列」
重算一遍，所以所有分栏宽度相同（除不尽的宽度会有 1px 的取整误差）；**删掉一个分栏时同样重算**
（只剩几列就均分成几份）。列内部的上下比例不受影响；只关掉某一列里的一行（列数没变）时不动
宽度，所以用户手动拖出来的列宽不会被悄悄抹掉。

**行高规则**：一个分栏里的窗口**只要增减就在这一栏把行高均分**（只均分这一栏，别的分栏不受
影响；有 gap 时按扣掉间隔之后的可用高度均分）——

- **新开一个窗口**（切开左下角那一格之后，整栏重新均分）；
- **在两行之间插入新的一行**（把窗口拖到某个窗口的上/下边缘、或者两行之间）；
- **关掉一个窗口之后**（这一栏还剩下两行以上时；如果整栏都没了，走上面「删掉分栏也等宽」）。
- **把窗口拖出这一栏之后**（拖到别的分栏 / 拖到别的工作区或显示器），这一栏剩下的行高均分。
  交换两个窗口的位置不会触发（两边的行数都没变，不该抹掉手动拖出来的行高）。
- **最小化 / 还原**同样算增减：最小化后剩下的行均分；还原时窗口从左下开始平铺，
  之后整栏同样均分。

**分栏宽度规则**：分栏数量只要变化（新增一栏、关掉/拖走最后一栏）就把所有分栏宽度均分。

需求 4 的「另一个窗口的四个边缘」在两层结构下是这样对应的：**左/右边** = 这一列的
左/右边界 → 在它旁边插出一个新分栏（整列让出一半，列里的窗口一起变窄、上下关系不变）；
**上/下边** = 这一列内部的横线 → 在这一列里插出新的一行。因为布局没有空位，最外侧窗口
的外侧边同时也是工作区边框，所以拖到工作区边缘和拖到窗口边缘是同一件事，行为统一。

**屏幕左右竖边优先**：指针只要落在左/右屏幕边缘的吸附范围内，**无论高度在哪儿**（正好压在
某条行分界线的延长线上、甚至跑到面板 / 停靠区那一段）都按「在这一侧插出一个新分栏」处理，
不会被行分界线抢走；离开边缘超过吸附距离（`edge-threshold`，默认 40px）之后才按行分界线插入新行。
此时的落点预览**高亮整条屏幕边框**（整个屏幕高度的一条 6px 主题色细条），而不是只标出某一
行那么高的一段。

**屏幕上下横边**：这条边上是面板 / 停靠区。分两种情况：

- 指针落在**被拖动窗口自己那一栏**对应的那一段（默认上下各 40px 的带内）→ **在本栏里正常
  平铺**：窗口被移到这一栏的**顶部 / 底部**（指针在上半 → 顶部），行高按现行规则均分；
  不会插出一整栏、也不会跑到别的分栏去。这一栏只有它一个窗口时没有别的行可换，保持原样；
- 指针落在**别的分栏**对应的那一段 → 把窗口移过去：贴着那一栏的上/下边缘插新行，
  正好压在分栏竖线上则插新分栏（离开横边带之后，行与行之间的分界线也照旧插新行）。

左右竖边的规则优先（角落处仍按左右竖边平铺）。
（注意：两层结构里不存在「占满半屏、其余窗口压到另一边」这种做法 —— 那会让列的高度
不一致、不再满足「每列占满整列高度」这个前提，所以扩展不提供这种模式。）

需求 4 里的「分栏」是插入的单位：拖到分界线上时，让位的是分界线某一侧紧邻的**一个单位**
—— 竖线旁是一整列，横线旁是一个窗口 —— 而不是指针下面那一个窗口：往两个分栏之间插入，
得到的是三个分栏；往一个分栏内部的横线上插入，得到的是三行同宽的窗口。两个窗口交换
位置时，两个格子（大小、位置）原样互换。

需求 6：**从最大化的窗口切走时，只取消它自己的最大化**。切到同一桌面上的另一个窗口（包括新打开
的窗口）时，原来那个窗口取消最大化、回到它自己的格子，新聚焦的窗口保持普通平铺 —— 最大化不会
跟着焦点搬家。跨桌面切换不动；拖动 / 缩放过程中不动；全屏窗口不参与这套（它是另一回事）。

历史上还试过两条更「积极」的规则，都已按说明撤回：一条是新窗口顶替并最小化焦点窗口，另一条是
关掉「第二个窗口」时把上一个窗口调回来 —— 现在新窗口一律按普通窗口平铺，关窗口也不会有任何
窗口被自动调回来。

**平铺生效期间**临时关闭 mutter 自带的贴边吸附（`org.gnome.mutter` 的 `edge-tiling`），
因为那套「拖到边缘 → 半屏 / 最大化」会和需求 4 的落点规则打架。关掉平铺（系统菜单里的开关、
「扩展」应用，或者卸载扩展）时把它**还回去**：恢复成接管之前用户的值。以前有一个「接管
mutter 的边缘平铺」开关，现在去掉了 —— 平铺开着就接管，关掉就归还。

这里有两个容易踩的坑，都已经处理：

- 关掉平铺之后扩展**彻底放手**（解除对所有窗口的接管、清空布局），不再摆布任何窗口。
  否则用户自己拖到屏幕边缘做的贴边吸附会被当成「平铺里的最大化」，很快又被撤掉 ——
  看起来就是系统自带的吸附坏了。
- 「接管之前的值」记在扩展自己的设置 `mutter-edge-tiling-backup` 里，而不是内存变量：
  Shell 上一次没干净退出（没机会恢复）时，dconf 里留下的那个 `false` 会被认出来是**我们**
  写的，下次照样能还回用户真正的取值。

系统菜单里那个平铺按钮除了开关，还提供「重新平铺所有窗口」「恢复所有最小化窗口」，以及
「平铺设置…」—— 直接打开本扩展的首选项页面，不用再去「扩展」应用里找齿轮。

`show-overview-when-empty` 默认关闭：打开后，当前桌面上没有任何非最小化窗口时会自动进入概览
（平铺模式下窗口经常被最小化，这样可以省掉「Alt+F1 / 左上角」那一下）。

需求 8 的「窗口之间不能重叠」把最大化的窗口排除在外：它铺满整个工作区，盖住其它窗口
是允许的，其它窗口照旧留在各自的格子里（布局被冻结），取消最大化时按原布局恢复 ——
也就是需求 6 里说的「恢复最大化之前的布局」。**平铺中的窗口之间**任何时候都不重叠：
如果这时新开一个窗口（焦点在某个普通窗口上），它仍然会立刻落进自己该在的格子，不会停在
mutter 随手放的位置上压到别人。「原来那个最大化窗口」会跟着焦点切走而取消最大化（见需求 6）。
对话框等浮动窗口和最大化窗口一样不参与平铺：它们保持 mutter 给的位置浮在上面，
既不占格子、也不进「不能重叠」的约束。

麻烦的是**文件选择器**这类窗口：它们（尤其 Wayland 下走 portal 的那种，窗口属于另一个进程）
先以普通窗口出现，过一会儿才把父窗口关系接上，而 mutter 这边 `transient-for` / `modal` 都不是
GObject 属性、没有 `notify::transient-for` 可听。所以除了「创建时判定」，还有三处复核：
窗口类型 / `skip-taskbar` 变化时、窗口拿到焦点时（以及之后 0.4s、1.2s 各一次）、以及每 2 秒
一次的兜底复核。任何已经在管的窗口一旦不再符合平铺条件，就从布局里**摘出去**（它的格子由
邻居吸收，之后只当普通浮动窗口对待），所以「迟到的对话框」不会一直占着平铺位置。

由于新窗口不再顶替、也不会最小化任何窗口，这类「迟到的对话框」退出平铺时不会有任何副作用要
收拾 —— 父窗口从始至终都在它自己的格子里。

**对话框弹出时不动父窗口**：焦点落到对话框（模态框、文件选择器……）上不算「用户切走了」，
所以父窗口**保持最大化**、不会因此被取消最大化；对话框开着期间父窗口也**不重新平铺**
（动父窗口会拽着对话框一起跳，格子暂时怎么变都先记着），对话框关掉之后再让父窗口回到
它该在的格子里。

**窗口自己改尺寸 / 挪位置时，邻近窗口跟着调整**：程序化 resize、视频切换比例、终端改行列
这类「窗口自主调整」，扩展不再把它拽回原来的格子，而是把它的格子改成新的矩形，由邻近窗口
吸收差值（同样走上面的级联规则）。如果变化的是这一侧根本没有分界线的方向（例如整列里唯一
那行的宽度），那就不可能在不改变结构的情况下自洽，仍按原来的方式回到格子里。

**稳定性**（这部分是为了「少做无谓的调整」）：

- 套用布局时，**已经在自己目标位置、也没有多余状态**的窗口不会再被请求一次几何 ——
  一次布局变化通常只会真正移动 1~2 个窗口（被切开的那一个 + 新窗口），布局没变化时
  一个请求都不发；
- 新窗口用 `HIGH_IDLE` 尽快落位，从创建到就位只发一次几何请求，避免可见的「先落在
  别处、再被挪过去」；
- 自动调整带保护：同一个窗口的**同一个「格子 → 实际尺寸」僵局**短时间内不会重复处理，
  复核次数也有限（最多 6 次、跨约 2 秒），避免和客户端来回拉锯把 shell 拖住；
  拖动 / 缩放期间任何复核都会让路，不碰任何窗口。

窗口有尺寸限制时，**其它窗口迁就它**：终端、播放器这类客户端会声明最小尺寸（也有声明最大
尺寸的），mutter 只能给到客户端允许的尺寸。扩展在摆放之后按 150 → 350 → 600 → 950 → 1400 →
2000ms 的梯级复核几何，每次都以「布局此刻期望的矩形」为准重写一次；只有在窗口**卡在同一个
尺寸上持续 900ms 以上**时，才认定那是客户端的尺寸限制，于是**改写那条分界线**：让它的格子
正好等于它的实际尺寸，多出/少掉的宽或高由相邻的那一列/那一行吸收 —— 于是既不重叠、也不留
空位。

「持续 900ms」这个条件是关键：取消最大化时 mutter 会异步把「最大化前的矩形」恢复回来，
那几百毫秒里窗口同样会「卡在同一个尺寸上不肯变」，但它不是尺寸限制 —— 据此改写布局会把
分界线钉到那个尺寸上（表现为相邻窗口突然被压到最小、窗口不再铺满可用空间）。复核会在这
期间重新写一次目标几何，所以这种临时状态会被纠正，不会被当成限制。

迁就时**优先动最近被拖动过的那条分界线**。典型场景：左中右三栏，把左边那栏拉大，中间那栏
被压到「客户端做不到」的宽度 —— 多出来的空间应该由**刚才被拉大的左边**让回来，而不是去推
右边那个用户根本没碰过、而且已经在自己格子里的窗口（以前固定先试右边，就会出现「中间窗口
的右边界位移、连累右窗口」）。另一条边动不了（贴着工作区边框）时才试另一侧。

上下排列完全同理（`n`/`s` 两条边）：拉大上面那行、中间那行碰到客户端最小高度时，由上面那行
让回空间，最下面那行不动。首选那条边被「通用最小值」钳住时，扩展会**放宽它再试一次**，
也不会转去推另一侧 —— 客户端的硬限制和 `minimum-window-size` 冲突时，宁可把这条边邻着的
那一块压小，也不去动用户没碰过的那一侧。

## 预留：最小化窗口 ↔ 平铺窗口 交换状态

`TilingManager.swapWindowStates(a, b)` 已经按「把一个最小化的窗口拖到某个平铺窗口上，
两者交换状态」的语义实现好了：

- 拖过来的窗口（原来最小化）**占住对方的格子**并恢复显示，尺寸一步到位；
- 对方被最小化、退出布局，腾出的正是这个格子；
- 账本同步：拖过来的窗口原来记下的「最小化前位置」作废（它已经占住格子了）；
  被最小化的那个之后如果由用户自己恢复，按「从左下开始平铺」的规则重新落位；
- 只接受「一个最小化 + 一个平铺中的普通窗口」，同一个工作区 / 显示器；对方是
  最大化 / 全屏、或者布局正被最大化窗口冻住时不动（返回 `false`）。

**为什么这一步是「预留」而不是直接能用**：最小化的窗口在 GNOME 里只能在概览中拖动，
而概览里的拖拽由 shell 自己处理、不会产生 mutter 的 `grab-op`，扩展现在接不到这次拖拽。
等概览的落点接上（或者由脚本触发）时，只需调用这一个方法。现在可以先在
Looking Glass 里试：

```js
const tiling = Extension.lookupByUUID('codex-tiling@codex.local').tiling;
const [minimized, tiled] = global.display.list_all_windows()
    .filter(w => w.get_window_type() === Meta.WindowType.NORMAL);
tiling.swapWindowStates(minimized, tiled);
```

```bash
journalctl -f -o cat /usr/bin/gnome-shell      # 实时日志
gnome-extensions info codex-tiling@codex.local # 状态
glib-compile-schemas ~/.local/share/gnome-shell/extensions/codex-tiling@codex.local/schemas
```

**先确认跑的是哪份代码**：扩展启用时会往日志里写一行带构建标记的
`[codex-tiling] 启用 codex-tiling <日期>`。**Wayland 会话必须注销后重新登录**才会加载
新装进去的代码（`gnome-extensions install` 本身不会热重载），装完没重登就会继续跑旧的。
日志里看不到新日期，说明跑的还是旧的。

跟窗口几何有关的动作还带了一组 `debug` 级日志（开始 / 结束缩放、被挡住的异常指针采样、
「迁就客户端的尺寸限制」改写了哪条分界线），排查「某个窗口为什么被挪了」时最有用 ——
`journalctl -f -o cat /usr/bin/gnome-shell | grep codex-tiling` 就能看到。

`swapWindowStates(a, b)` 等钩子做实验。

## 已知限制

- 每个「工作区 × 显示器」独立维护一份布局；跨显示器移动按跨工作区同一套规则处理。
- 平铺布局由扩展主导：拖动窗口边缘时，改动的是它这条边重合的那条分界线 ——
  左右边对应「列宽」（整列一起变），上下边对应「行高」（同一列里的行一起变）；
  如果这条边本身就是工作区的边框（没有对应的分界线），松手后窗口会回到自己的格子。
- 客户端如果设置了最小尺寸或固定比例（例如终端、部分 Wayland 应用），可能无法精确填满格子；
  扩展会按上面的梯级复核几何，并在确认客户端做不到之后让布局迁就它（约 1~2 秒）。
  Wayland 下扩展无法事先知道客户端的最小尺寸，所以拖动分界线越过这个限制的那一瞬间，
  边界会先跟着鼠标（相邻窗口会暂时被盖住），松手、复核之后才由布局迁就它 —— 这是拿不到尺寸提示时
  的取舍：宁可让边界跟手，也不让分界线被猜出来的尺寸钉住。
- 取消启用时窗口会保持当前的平铺位置（不会还原成启用之前的样子）。
- 本项目已用单元测试、模拟 shell 的完整流程和真实类型库的接口检查验证；
  真机图形会话里的端到端测试（`tests/live/run.sh`）需要在能启动 GNOME Shell 的环境里运行。

## 卸载

```bash
gnome-extensions disable codex-tiling@codex.local
gnome-extensions uninstall codex-tiling@codex.local
```

禁用时扩展会把临时改过的 `org.gnome.mutter` `edge-tiling` 恢复成原值。
